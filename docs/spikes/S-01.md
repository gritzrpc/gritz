# S-01: Clean master, reuseport and CPU scaling

- Date: 2026-10-02.
- Environment: [shared environment](README.md), two Linux CPUs.

The parent loads grpc and generated service definitions, then forks without
creating a native gRPC object. Each child binds the same fixed address with
`grpc.so_reuseport=1`. Independent local subchannel pools prevent the client
connections from collapsing into one shared connection.

Run each configuration separately inside the Linux container:

```sh
WORKERS=1 CPU_MS=5 ruby spikes/s01_reuseport/run.rb
WORKERS=2 CPU_MS=5 ruby spikes/s01_reuseport/run.rb
WORKERS=4 CPU_MS=5 ruby spikes/s01_reuseport/run.rb
```

The four-worker connection tally was 23 / 13 / 16 / 12 connections,
max/min 1.92. All four PIDs responded. An earlier Echo smoke run completed
84,230 requests in 5.014 s with zero errors.

Raw CPU results: [one](results/s01_w1_linux.json),
[two](results/s01_w2_linux.json), [four](results/s01_w4_linux.json).

Clean master and shared binding work for the measured version. **The required
four-worker ≥3.4× gate is pending:** this two-CPU machine cannot evaluate it.
These five-second Ruby-client runs are exploratory; they do not replace the
dedicated ≥4-core runner, ghz, warmup and repeated 30-second measurements.
Only grpc 1.83.0 was exercised; no lower supported grpc version was established.
