# S-03: Guard gRPC before native allocation

- Date: 2026-10-02.
- Environment: Linux Ruby 3.4.11 and macOS Ruby 4.0.6, grpc 1.83.0.

```sh
ruby spikes/s03_fork_guard/probe.rb
HOOK=initialize ruby spikes/s03_fork_guard/probe.rb
```

The class singleton `new` hook blocked all seven named entry points in the
parent, reported the calling file and line, and forwarded their real arguments
successfully in forked children: Channel, Server, ChannelCredentials,
ServerCredentials, CallCredentials, ClientStub and RpcServer.

The proposed instance `initialize` hook detects calls **too late**. Native
`grpc_rb_channel_alloc` invokes `grpc_ruby_init` before Ruby `initialize` runs.
Raising from `initialize` therefore still contaminates the parent; subsequent
child construction fails with the grpc before/after-fork RuntimeError.
The Linux comparison recorded `child_forwarded=false` for all seven entries.

Raw logs: [class new](results/s03_linux_new.json),
[initialize](results/s03_linux_initialize.json).
Relevant primary source: [grpc 1.83.0 channel allocator](https://github.com/grpc/grpc/blob/v1.83.0/src/ruby/ext/grpc/rb_channel.c).

The successful [S-01](S-01.md) child RPCs also establish that requiring grpc and
generated definitions alone leaves the measured parent usable for clean fork.

Use a pre-allocation class `new` hook for normal constructors. A complete
ForkGuard must separately address direct `allocate` and resources created
before guard installation. These paths and C-internal allocation bypasses were
not covered; this probe does not establish complete detection coverage.
